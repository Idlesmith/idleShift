# 計測計画（F-1）

状態: 計画のみ（T-249、G-18）。測定はまだしていない。
ここで決めた判定基準は、結果を見てから変えない。変える場合は理由と変更前の基準を残す。

## 共通の約束

- 本番のデータフォルダーは読み取りのみ。測定は `IDLESHIFT_HOME=<一時フォルダー>` の別環境で行う。
- 生データ（ログ、DBの行、ツール呼び出しの記録）は `docs/evidence/raw/<主張>/<日付>/` に保存し、加工した結果は `docs/evidence/<主張>.md` に書く。
- 結果ごとに「誰が・いつ・どの版（コミットID）・どのアプリの版で」測ったかを書く。
- 都合の悪い結果も書く。条件を満たせなかった試行も消さない。
- 分類は3つ:
  - **実証済み**: 下の基準を、再現手順どおりに2回以上満たした。
  - **条件付き**: 一部のアプリ・条件でだけ満たした。条件を明記する。
  - **未実証**: 測っていない、または基準を満たさなかった。

## 主張(a) 待機中は使用枠をほぼ使わない

### 仕組み（コードから読んだ事実）

- `next(wait_seconds)` はサーバー側で応答を保留する。保留の長さは `holdFor` で決まり、上限は 3600 秒（`src/core.mjs:37` の `holdCap`）。
- アプリごとに「保留に耐えられた長さ」を学習する。初回は 50 秒（`holdInitial`）、耐えられると次は倍、失敗した長さは24時間避ける（`src/core.mjs:783-789`, 1722-1724）。
- つまり **最初の数回は短い待機の繰り返しになり、1時間待機に達するまでに数回の呼び出しが要る**。この立ち上がりも測定に含める。

### 測るもの

1. サーバー側: 待機1時間あたりの `next` 呼び出し回数と、各呼び出しの保留時間（サービスのイベント記録とDBの `clients.hold_ok_ms`）。
2. アプリ側: 同じ1時間に、モデルが応答を生成した回数（＝ツール結果を受けてモデルが動いた回数）。原則 `next` の回数と同じになるはずだが、アプリによって途中で進捗通知や再接続が入るかを確かめる。
3. 使用枠: 取れるアプリだけ、待機前後の使用量表示を記録する（Claude Code の `/usage` 相当の表示、Codex の使用量表示など）。取れないアプリは「呼び出し回数のみ実測」と書く。
4. 比較対象: 同じ1時間を「`wait_seconds=0` で60秒ごとに呼ぶ」ポーリングにした場合の呼び出し回数（計算値でよい: 60回）。

### 手順

- A. 自動部分（AIなしで再現できる）: テスト用のスクリプトで中継を起動し、MCPクライアントの代わりに `next(wait_seconds=3600)` を繰り返し呼ぶ。提示が出ない状態で、保留時間の推移（50秒→100秒→…→3600秒）と1時間・3時間あたりの呼び出し回数を記録する。担当: F-4。
- B. 実アプリ部分（人の手が要る）: Claude Code、Codex、Antigravity のそれぞれで、空のプロジェクトに join させ `next(wait_seconds=3600)` で待機させたまま1時間放置。前後の使用量表示をスクリーンショットで残す。これは人の操作が要るので、F-4 が手順を書いて ask_human で依頼する。

### 判定基準

- **実証済み**: 学習が済んだ状態（保留が3600秒に達した後）で、3つのアプリのうち少なくとも1つで、1時間あたりの `next` 呼び出しが **2回以下**、かつ使用量表示の変化がそのアプリの最小単位以下。
- **条件付き**: 呼び出し回数は2回以下だが使用量の実数が取れない（「呼び出し回数のみ実測」）、またはアプリによって保留が短く切られ1時間あたり 3〜12回になる。条件（アプリ名と保留の上限）を書く。
- **未実証**: 1時間あたり 13回以上（5分以下の間隔）になる、または測っていない。
- 立ち上がり（学習前）の回数は別に記録し、宣伝文では「学習後」と明記する。

## 主張(b) 使用枠と再開時刻を見て割り当てる

### 仕組み（コードから読んだ事実）

- AI が `report` に `quota`（state, reset_at）を付けるか、`kind=limit` を送ると、そのアプリは `limit_reported` になり、`reset_at`（無ければ30分 `limitFallback`）まで提示されない（`src/core.mjs:376-399`, 1043, 1323）。
- 再開時刻を過ぎても「回復した証拠」ではないので、1回だけ試す扱い（`tried_after_reset`、`src/core.mjs:395`, 1046-1047）。
- 人がラベルごとに5時間・7日の上限（件数・分）を設定でき、超えると提示しない（`usageBlock`、`src/core.mjs:578-592`）。
- 提示先の選択は `pickOffer`（`src/core.mjs:990`）と 911 行の候補絞り込み。

### 測るもの

1. 2つの参加者（別クライアント）がいるとき、片方が `limit`（reset_at=+X分）を申告した後の提示先。
2. reset_at を過ぎた直後に、申告した側へ再び提示されるか（1回の試し）。
3. 人が設定した5時間上限に達した参加者が飛ばされ、境界時刻を過ぎると戻ること。
4. 申告が無い（unknown）参加者の扱い。

### 手順

- テスト環境（別HOME）で時計を差し替えられる中核（既存テストの `helpers.mjs` の方式）を使い、上の1〜4を自動テストとして書く。テスト名と出力を生データとして残す。担当: F-2。
- 実アプリでの実演（台本用）は、2つのアプリで1回ずつ limit を申告させ、画面で提示先が変わる様子を録画する。人の操作が要る部分は ask_human。

### 判定基準

- **実証済み**: 1〜4の自動テストがすべて通り、かつ実アプリ2つで1回以上、申告後に提示先が切り替わったことを記録した。
- **条件付き**: 自動テストは通るが実アプリでの記録が無い。「サーバーの判定として実証、実アプリでは未確認」と書く。
- **未実証**: 1〜4のどれかが通らない。
- 注意: これは「AI の申告と人の設定に従う」ことの実証であり、IdleShift が各社の使用量を **自分で読み取る** わけではない。宣伝文でそう読める書き方はしない。

## 主張(c) 会話を捨てても進捗が残る

### 測るもの

1. タスクを claim して progress を送った会話を、途中で終了（会話を消す／アプリを閉じる）した後、
   - 同じラベルで新しい会話から `join` すると、担当中のタスクと世代が戻るか。
   - 別のAI（別クライアント）が、担当期限切れの後に同じタスクを引き継げるか。そのとき前の担当の handoff・progress・evidence が assignment に含まれるか。
2. ゴールの要約（summary/next_step）・証拠・判断が、サービスの再起動の後も残るか。
3. 引き継いだAIが、前の会話の内容を読まずに作業を完了できるか。

### 手順

- 自動部分: 既存の e2e テストの方式で、claim→progress→接続切断→再join（同ラベル）→assignment の内容を検証。担当期限切れ→別参加者へ提示→handoff の有無を検証。サービスの再起動を挟む版も作る。担当: F-3。
- 実アプリ部分: Claude Code でタスクを途中まで進めて会話を終了し、Codex（または別の Claude 会話）で引き継いで完了させる。両方の会話記録と黒板の記録を残す。人の操作が要る部分は ask_human。

### 判定基準

- **実証済み**: 自動テストがすべて通り、実アプリで「別のAIが引き継いで完了」が1回以上記録された。
- **条件付き**: 自動テストのみ、または同じアプリ・同じラベルの再参加でのみ成立。
- **未実証**: 再join で担当が戻らない、引き継ぎ時に前の記録が渡らない、または測っていない。
- 注意: 残るのは黒板に書かれた内容（要約・証拠・報告・ファイル）だけ。会話中に考えたが書かなかった内容は残らない。宣伝文ではこの限界も書く。

## 必要な環境

- Windows 11、Node（package.json の engines の版）、テスト用の一時フォルダー。
- 実アプリ部分: Claude Code、Codex、Antigravity のうち2つ以上にログイン済みのPC。人の操作が要る。
- 時計を進めるテストは既存の `tests/helpers.mjs` の方式に合わせる（外部ライブラリは追加しない）。

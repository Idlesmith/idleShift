## 1. 自動部分: 保留の長さの立ち上がり（実測）

方法: 一時 `IDLESHIFT_HOME` で本物のサービスと中継（`bin/idleshift.mjs mcp`）を起動した。テスト用クライアント（`f4-test-client`）は保留を最後まで待ち、仕事を出さない（ゴール無し）状態で `next(wait_seconds=3600)` を繰り返した。本番には触れていない。

生データ（2026-11-12）:

| 回 | 開始(秒) | 保留(秒) | 結果 |
|---|---|---|---|
| 1 | 0 | 50.0 | none |
| 2 | 50 | 100.0 | none |
| 3 | 150 | 200.1 | none |
| 4 | 350 | （400秒の予定。試験の制限時間で打ち切り） | ― |

- `holdFor`（`src/core.mjs:799-806`）のとおり、受理されるたびに倍に伸びた。この調子なら、3600秒に届くのは 50→100→200→400→800→1600→3200→3600 の8回目、開始から約1時間45分後。
- **立ち上がりの約1時間45分の間に、`next` の呼び出しは7回**かかる。
- サービス側で倍に伸ばすのは「前回の保留をクライアントが最後まで受け取れた」ときだけ。

## 2. 本番の記録: 実際のアプリが耐えた保留の長さ（読み取りのみ）

方法: 本番の `%LOCALAPPDATA%\IdleShift\idleshift.db` を `node:sqlite` の `readOnly` で開き、`clients` テーブルを読んだ（2026-11-12）。書き込みはしていない。

| アプリ（clientInfo.name） | 版 | 受理された最長の保留 `hold_ok_ms` | 途絶えた保留 `hold_fail_ms` | 待機中の作業完了 `unattended_cycles` | 待機の再開 `wait_resumes` |
|---|---|---|---|---|---|
| claude-code | 2.1.321 | 約333秒 | 約100秒 | 36 | 51 |
| codex-mcp-client | 0.167.0-alpha.3.2 | 約200秒 | 約137秒 | 26 | 78 |
| antigravity-client | v1.0.0 | 約152秒 | 約150秒 | 69 | 594 |

読み取れること:
- **3つのアプリとも、受理された保留は約2.5〜5.5分で、上限の3600秒には遠い**。途絶えた記録は約1.7〜2.5分。
- 途絶えた長さが24時間以内に記録されていると、次の保留はその8割が上限になる（`core.mjs:804`）。各アプリには、ツール呼び出しの待ち時間の上限（タイムアウト）があり、それを超えると途絶えるとみられる（推測。各アプリのタイムアウトの値は未確認）。
- このため、実際の待機は1時間あたり約11〜24回の `next` 呼び出しになる（3600秒 ÷ 150〜333秒。計算値）。

注意:
- `hold_fail_ms` が `hold_ok_ms` より短いのは、途絶えた時点と受理された時点が別の機会だから（例: アプリの再起動、別の会話）。途絶えの原因を区別する記録は無い。
- 1回の `next` ごとの記録（イベント）は DB に無い。呼び出し間隔の分布は出せず、上の回数は計算値。

## 3. 使用枠への影響（未計測）

- 呼び出し1回ごとに、アプリの中でモデルが1回応答する（ツールの結果を受けて、次に `next` を呼ぶ）。この1回が使用枠をどれだけ使うかは、アプリとモデル、会話の長さで変わる。会話が長いほど、1回の応答で読み直す文脈が大きくなる（推測）。
- 実アプリでの使用量表示の変化は、人の操作が要るので未計測。依頼を ask_human で出した。

## 4. 判定（plan.md の基準による）

- 基準「学習後に1時間あたり2回以下」: **満たしていない**。実際のアプリでは、学習しても保留が2.5〜5.5分で頭打ちになり、1時間あたり約11〜24回になる。
- 基準「13回以上は未実証」: 3アプリとも13回以上の範囲に入る（claude-code は約11回で境界付近）。
- **暫定の分類: 未実証**。宣伝で「待機中は使用枠をほぼ使わない」とは、今は書けない。
- 書ける範囲の事実: 「1分ごとに確認する方式（1時間60回）と比べ、実際のアプリで1時間あたりの呼び出しは約11〜24回に減る。」（計算値。使用量の実数は未計測）

## 5. 改善の余地（設計の提案。実装は別のタスク）

1. 中継が `notifications/progress` を20秒ごとに送っている。アプリがこれでタイムアウトを延ばすなら保留は伸びるはずだが、記録を見る限り延びていない（3アプリとも数分で途絶えている）。各アプリがツール呼び出しのタイムアウトを延ばす設定を持つか調べる（Claude Code の MCP のタイムアウトの環境変数など。未確認）。
2. 設定で延ばせるアプリは、README に設定方法を書き、測り直す。
3. 1回の呼び出しで使う量を減らす: `none` の応答と guide を短くし、会話の文脈が伸びないようにする。

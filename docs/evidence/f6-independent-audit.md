## 1. 独立点検結果（主張別）

### 主張(a)「待機中は使用枠をほぼ使わない」（F-4）
- **測定レポート**: `docs/evidence/waiting-cost.md`（P-6 担当）
- **点検結果と事実の整合性**:
  1. **保留時間の立ち上がり（実測）**:
     - 一時 `IDLESHIFT_HOME` における `next(wait_seconds=3600)` の実測ログでは、50秒 → 100秒 → 200秒 と倍々に伸長することを確認。
     - 計算上3600秒に達するには8回の呼び出し（約1時間45分）が必要。
  2. **本番 DB（読み取り専用）の実測値**:
     - `%LOCALAPPDATA%\IdleShift\idleshift.db` の `clients` テーブルの実測値（claude-code: 最長333秒/途絶100秒, codex: 最長200秒/途絶137秒, antigravity: 最長152秒/途絶150秒）を確認。
     - 実際のアプリではクライアント側タイムアウトや途絶えにより、最長保留は約2.5〜5.5分にとどまり、上限3600秒には到達していない。
  3. **都合の悪い結果（重要）**:
     - 1時間あたりの `next` 呼び出し回数は、理想値（1回）に対して**実測計算値で約11〜24回**発生している。
     - `plan.md` で事前に定めた「1時間あたり2回以下で実証済み、3〜12回で条件付き、13回以上で未実証」という判定基準に基づくと、Codex（約18回）やAntigravity（約24回）は13回以上の「未実証」基準に該当する（Claude Codeの約11回も境界線付近）。
     - 加えて、呼び出し1回あたりのトークン消費量・残高推移は人手操作が必要なため未計測。
- **最終分類**: **未実証**
- **宣伝上の扱い**: 「待機中は使用枠をほぼ使わない」という無条件のコピーは掲載不可。「毎分ポーリング（毎時60回）に比べ、実測で毎時約11〜24回の呼び出しに抑制される（トークン消費量は未実測）」と正確に限定して表記する。

### 主張(b)「使用枠と再開時刻を見て割り当てる」（F-2）
- **測定レポート**: `docs/evidence/quota-routing.md`（参照: `quota-allocation.md`）
- **再現性検証**:
  - `node --test tests/evidence-quota-routing.test.mjs` を独立実行し、`tests 1, pass 1, fail 0`（所要時間約88ms）で再現成功を確認。
- **点検結果と事実の整合性**:
  1. `report(kind='limit', reset_at)` による新規提示の即時遮断（`limited=true`）、`reset_at` 経過後の stale 遷移と 1 回試行許可がコード（`src/core.mjs:389-415, 1039-1060`）通り動作。
  2. 人手設定の 5 時間上限（`limit_5h_claims`）による `usageBlock` 発動と解除がコード（`src/core.mjs:578-605`）通り動作。
  3. **都合の悪い結果・実装上の注意点**:
     - `kind='limit'` で戻されたタスクには `prefer = 報告者` が付与されるため（`src/core.mjs:1341`）、`preferGrace`（5分間）が経過するまで他ワーカーへ即座に再提示されない。
     - `quota: { state: 'low' }` はアドバイザリ表示（detail に「残り少」）のみであり、自動停止や配分除外は行わない（AI側の自己申告 `kind='limit'` または人手上限設定が必須）。
     - 実アプリ 3 台を同時稼働させた長時間の録画実証は未実施。
- **最終分類**: **条件付き**（自動テスト全件合格。ただし実アプリ間の実測録画が未取得のため）

### 主張(c)「会話を捨てても進捗が残る」（F-3）
- **測定レポート**: `docs/evidence/continuity.md`（P-6 担当）
- **再現性検証**:
  - `node --test tests/evidence-continuity.test.mjs` を独立実行し、`tests 1, pass 1, fail 0`（所要時間約980ms）で再現成功を確認。
- **点検結果と事実の整合性**:
  1. クライアント切断後に同一 `label` で再接続した場合、同一 `participant` で `resumed: true` となり、保持タスクと新世代 `gen` が正しく復元される。
  2. サービスプロセスの停止・再起動を跨いでも、SQLite（WAL）上のゴール要約・証拠・タスク状態・報告履歴が完全に保持される。
  3. リース期限切れ（30分）によりタスクが `open` に戻り、別の AI ワーカーが過去の要約・証拠・報告を参照して引き継ぎ完了できる。
  4. **都合の悪い結果・境界条件**:
     - チャット内の思考ログそのものは引き継がれず、黒板（`goals`, `tasks`, `evidence`, `reports`）およびワークスペースに明示的に書き出されたデータのみが引き継ぎ対象である。
     - 実際の異なる AI デスクトップアプリ間（例: Claude Desktop と Codex CLI 間）の実機引き継ぎ録画は未実施。
- **最終分類**: **条件付き**（実サービス・実リレーの自動テストで全シナリオ実証済み。実アプリ間の実機引き継ぎ録画が未実施のため）

# サービス再起動後の待機の継続（A-5 (3) の調査）

実装しなかった理由: `src/relay.mjs` は A-3（T-221、別の担当）が編集中で、未コミットの変更（+62/-10行）がある。同じファイルを並行して変えると上書きの恐れがあるため、A-3 の取り込み後に別タスクで行う。

## 今の動き（コードから）

1. AI が `next(wait_seconds=3600)` で待機中、中継（relay）はサービスへの名前付きパイプ接続の上で応答を待っている。
2. サービスが止まる（コード更新による再起動、`stop`、PC のスリープ復帰など）とパイプが閉じ、`makeLink` の `fail` が待機中の要求を「IdleShiftのサービスとの接続が切れました。もう一度呼び出してください。」で失敗させる（`relay.mjs` の `makeLink`）。
3. 中継はこれを `service_unavailable` の拒否として AI に返す（`runRelay` の catch）。
4. AI が次に何か呼ぶと `getLink` が再接続（必要ならサービスを起動）するが、サービス側は再起動後の最初の呼び出しに `rejoin_required` を返す（README「割当の状態機械」）。
5. 多くの AI は、このエラーを受けた時点で会話のターンを終えてしまい、人が「開始の一言」を貼るまで戻らない。これが「人の一言なしには戻れない」原因。

## 中継側でできること（案）

中継が、AI の代わりに「再接続 → join → next」をやり直す。

- 中継は、その接続で最後に成功した `join` の引数（`root`、`label`）と、返ってきた `participant` を覚えておく。中継は状態を持たない方針（README）だが、これは DB の写しではなく「この AI が名乗った内容」だけなので方針に反しないと考える。
- `tools/call` の `next` がパイプ切断で失敗したときだけ、次を行う:
  1. 少し待って（例: 1秒、3秒、10秒…最大で残りの待機時間まで）再接続を試す。サービスが無ければ起動する（`connectService` の autostart と同じ）。
  2. 覚えている `root`・`label` で `join` を呼ぶ。`participant` が変わったら覚え直す。
  3. 元の `next` を、残りの待機時間で呼び直す。
  4. 結果をそのまま AI に返す。AI から見ると、長い `next` が1回返っただけになる。
- `join` で担当中のタスクが戻ってきた場合は、`next` が `resume` を返すのでそのまま渡す。
- 以下の場合はやり直さず、今と同じエラーを返す:
  - `next` 以外の呼び出し（claim や report は二重実行の危険があるため。report は `report_id` で二重登録を防げるが、初版では対象外にする）。
  - `join` が `registered:false` や拒否（参加取消、アーカイブ）を返したとき。
  - 認証失敗（データ置き場が別、トークン不一致）。これは A-3 の診断に任せる。
  - 再接続が待機時間内に成功しなかったとき。
- `join` を一度もしていない中継では何もしない。

## 注意点

- 再起動の理由が「コードの更新」の場合、中継自体は古いコードのまま動き続ける。中継とサービスの版が違うときの扱い（版の不一致を知らせる）は、A-3 の診断と合わせて決める。
- 進捗通知（progress）を出しているホストでは、やり直しの間も通知を続ける。
- 1回の `next` の中でやり直す回数に上限を付ける（例: 5回）。サービスが起動直後に落ち続ける場合に、使用枠を消費せず中継の中で止まるようにする。

## テスト案

- e2e テストの方式で、中継を起動 → join → `next(wait_seconds=30)` の途中でサービスを `stop` → すぐ別のサービスを起動 → `next` が `none`（または `offer`）で正常に返り、`service_unavailable` にならないこと。
- 参加取消の後の再起動では、やり直さずにエラーを返すこと。
- `claim` の途中で切れた場合は、今までどおりエラーが返ること。

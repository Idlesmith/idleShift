## 1. 技術的な定義

IdleShift は、1台の Windows PC で動く **ローカルの黒板サービス** である。複数の AI アプリ（MCP クライアント）が、それぞれ起動する stdio の中継を通して、1つの常駐プロセスが持つ SQLite の状態を共有する。ゴール・タスク・担当・許可・予算・完了の判定は、AI ではなくこのサービスが行う。AI は `next` で仕事を取りに来る（サービスが AI を起動するのは、人が有効にした場合だけ）。（01 §1〜3）

## 3. 自己開発の経緯と検証可能な実績

- 初版は IdleShift を使わずに作られた。「Built with itself」は不正確で、上限は **「Built and improved with itself (since the initial baseline)」**。（02 §6）
- 記録で確認できる期間: 2026-11-10 21:18 〜 2026-11-12 22:50（約49.5時間）。（02 §6.1）
- 完了済みのゴール3つ（G-2〜G-4）で、66タスク中62件が受理され、レビュー33回のうち11回が差し戻しだった（33.3%）。レビューはすべて実装者と別の参加者が行った。（02 §3・§5。DB の数値は D-5 で読み直していない＝未確認）
- 人の明示的な判断は5件（完了の確定3、権限の質問2）。ただし、各 AI アプリに開始の一言を貼る人の操作は DB に記録されないので、この数には含まれない。（02 §4、D-5 の指摘）
- 差し戻しが品質を上げた実例: 復元時の世代の衝突を2回の差し戻しで見つけ、DB の外に記録する方式へ設計を変えた。（02 §3.2）
- テストは 39 → 99 → 140 → 160 → 178 件に増えた。178 件全部の成功は 2026-11-13 に P-6 が確認。（02 §5、T-277）

## 4. 競合比較（要点）

他製品にもある機能（IdleShift 固有の発明とは書かない）（03 §3.1）:
- MCP による複数 AI の共有ボード（ConnectR、Marcus、agent-tasks、stringwork、Befall）
- 会話に依存しない状態の保存と、期限切れの再割り当て（Marcus、ConnectR、stringwork、agent-tasks）
- 既存のサブスクの活用（Chorus、ConnectR、stringwork、MCO、Umbel、Tutti）
- git ワークツリーによる分離（ConnectR、stringwork、Umbel が先行）

調査時点で IdleShift に特徴があるとみられる点（03 §3.2。一次情報の読み取りによる。抜き取り2件は D-5 で一致を確認）:
1. サーバーが AI を全権限のフラグで起動する型ではない。人が普段使うアプリから `next` で取りに来て、アプリごとに保留の長さを学習する（例: Chorus は `--dangerously-skip-permissions` や `--full-auto` で起動する。D-5 で確認）。
2. AI の上限の申告（limit・reset_at）と、人が設定した5時間・7日の上限による割当の抑制を明示的に持つものは、比較した9製品に見当たらなかった。
3. 委任範囲・予算・完了の確定を、サービス側で強制する。
4. Windows で、npm の依存なしに動く。

先行されている点: git 分離とファイルのロック、Mac/Linux 対応、公開の実績（Tutti は約3,900スター、MCO は554スター）。

## 7. 推奨ポジショニング

**「AI を勝手に動かさない、人が手綱を持つ、ローカルの共有作業台」**。速さや自律の度合いではなく、「普段のアプリのまま、人が許可と完了を握ったまま、複数の AI に分担させる」ことを主にする。理由: 自律・並列・既存サブスクの活用では競合が先行するか同等だが、「全権限で起動しない」「人だけが許可と完了を決める」「上限の申告で回し先を変える」は、比較の範囲で IdleShift の特徴として裏付けがあるため（4章）。

## 結論: なぜ既存の AI エージェント利用者が導入する価値があるか

すでに複数の AI アプリを使っている人にとって、IdleShift の価値は「自律で何でもやる」ことではない。**普段のアプリと権限設定のまま、1つの黒板で仕事を分け、進捗を会話の外に残し、上限に達した AI を避けて回し、許可と完了の決定を人の手に残す**ことにある。この組み合わせは、比較した9製品の範囲では裏付けのある特徴である（4章）。一方で、待機中の使用量、マージ画面、セキュリティの2件の修正は未完了・未実証であり、それらが済むまでは「条件付き」として説明すべきである。

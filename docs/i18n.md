## 2. 文言の持ち方

- 辞書は言語ごとの ES モジュール: `src/i18n/en.mjs`、`src/i18n/ja.mjs`。キー → 文字列または関数。

```js
// src/i18n/en.mjs
export default {
  'root.not_absolute': raw => `Use an absolute path (for example C:\\work\\project). Given: ${raw}`,
  'root.missing': raw => `Folder not found: ${raw}`,
  ...
};
```

- 取り出しは `src/i18n/index.mjs` の `t(lang, key, ...args)`。キーが無い言語では英語に落とし、英語にも無ければキーそのものを返す（テストで検出する）。
- GUI は同じ辞書を使いたいが、GUI は `gui/` 以外を配信しない（`service.mjs` の静的ファイルの制限）。そこで GUI 用の辞書は `gui/i18n/en.js`・`gui/i18n/ja.js` に分け、サーバー側と共有しない。キーの重複は少ない（画面の文言と AI 向けの文言はほぼ別）。
- **拒否は「コード＋引数」を正にする**。`Refusal` は今も `code` を持っているので、`new Refusal(code, key, args)` の形にして、文言は返す直前に言語に合わせて作る。テストは文言ではなく `code`（必要なら `key`）で照合する。

## 3. 言語の決め方

- 人向け（GUI、通知、CLI の表示）: 設定 `ui_language`（`auto` / `en` / `ja`）。`auto` は GUI ならブラウザーの `navigator.language`、CLI と通知なら OS のロケール（`Intl.DateTimeFormat().resolvedOptions().locale`）。既定は `auto`。GUI の設定画面で変えられる。
- AI 向け（MCP の応答）: 下の4。

## 4. AI 向けの文面は何語にするか

**既定は英語**にし、設定 `ai_language`（`en` / `ja` / `ui`＝人向けと同じ）で変えられるようにする。

理由:
- どのモデルも英語の指示に最もよく従う。拒否の理由や guide の「してはいけないこと」は正確に伝わることが重要。
- 同じ内容なら英語の方がトークン数が少ないことが多い（日本語は1文字あたりのトークンが多くなりがち。実測はしていない）。待機と報告を何度も繰り返すので、毎回の応答の長さは使用枠に効く。
- ツールの説明はすでに英語なので、応答も英語にすると一つの言語にそろう。

ただし:
- **人が書いた文（ゴールの題名、完了の証拠、メモ）と、AI が書いた文（`untrusted_ai_*`）は翻訳しない**。書かれた言語のまま渡す。
- AI が人に向けて書く文（報告の要約、ask_human の質問）は、人が読む言語で書くよう guide で指示する（「Write summaries and questions for the human in <ui_language>」）。
- `ai_language` はプロジェクトごとではなく全体の設定にする（初版）。

## 5. DB に保存済みの日本語文の扱い

DB には、作られた時点の言語の文が残っている:

| 保存先 | 中身 | 方針 |
|---|---|---|
| `decisions.question` | 完了候補・予算・無進展などの判断の質問文（プログラムが作る） | 新しい行には `kind` と引数（JSON）も保存し、表示のときに言語に合わせて組み立てる。既存の行は保存された文をそのまま表示する（翻訳しない） |
| `tasks.title`/`body`（`author_kind='program'` の進行役タスク） | 「進行役：ゴールを小目標に分解し…」など | 新しい行は作るときの `ai_language` で書く。既存の行はそのまま |
| `events` | イベントの種類はキー（`root_added` など）で、データは JSON | 変更不要。表示側で訳す |
| 人や AI が書いた文 | ― | 翻訳しない |

DB の版を v6（または G-14 と合わせて v7）に上げ、`decisions` に `message_key TEXT`、`message_args TEXT` を追加する。既存の行は NULL のままで、表示は `question` を使う。

## 6. テストへの影響

- 日本語の文言で照合している約30行（9ファイル）を、`code` や `key` での照合に変える。文言自体を確かめたいテストは、言語を固定（`ja`）して照合する。
- 新しいテスト:
  - 英語と日本語の辞書のキーが一致していること（片方にしか無いキーが無い）。
  - 関数の文言の引数の数が両言語で一致していること。
  - `ai_language=en` で join → next → claim の応答に日本語が含まれないこと（人や AI が書いた文を除く）。
  - GUI の辞書のキーが、`app.js` で使われているキーを全部含むこと（静的に照合）。

## 7. 段階的な移行の順番

1. 仕組みだけを入れる: `t()`、辞書、`ui_language`・`ai_language` の設定。辞書は日本語だけにし、今の文言をそのまま移す。テストは全部通る（動きは変わらない）。
2. AI 向けの文面: guide、assignment の注意書き、`Refusal` と plan の `fail(` を辞書へ移し、英語を書く。既定を `en` にする。テストを `code` 照合へ変える。
3. 判断（decisions）の質問文: `message_key` と移行。
4. GUI: `app.js` の文言を `gui/i18n` へ移し、英語を書く。`<html lang>` を設定に合わせる。
5. 残り: hosts の名前、開始の一言（英語版を用意。どちらを出すかは `ui_language`）、CLI の表示、通知。
6. README.md（英語）と README.ja.md（E-7）。

各段階は単独で取り込めて、途中でも日本語の利用者には動きの変化が無い（2の後、AI 向けの文面だけが英語になる）。

## 8. 決めていないこと（人に聞くこと）

- AI 向けの既定を英語にすることで、日本語でしか指示を出さない利用者に違和感がないか。違和感がある場合は既定を `ui` にする。初版は英語を既定にし、設定で変えられるようにしておけば足りると考える。
- 翻訳の質の確認者（英語の画面文言のレビュー）を誰にするか。
